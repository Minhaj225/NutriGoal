# Feedback version 2 rollout

Create the unique `{ studentId: 1, mealId: 1 }` index on `mealfeedbacks` before enabling rating writes. The service uses a MongoDB transaction, so the target database must support transactions. Verify this with a small write, retry, and rollback test in staging. Deploy the backend and frontend together so a star click sends one authenticated `/rate` request.

For new feedback, `studentId` is the authenticated account ID. One row stores the current numeric rating and/or explicit thumbs response. A rating implies `liked` at four or five stars; an explicit thumbs response may override it. `feedbackAt` records feedback time, not consumption. `Meal.ratingSum`, `totalRatings`, `popularity`, and `averageRating` are version 2 summaries of distinct current numeric ratings. The first version 2 rating on an older meal snapshots its prior summary in `legacyRatingSummary` and starts the new count from zero. Keep legacy embedded `Student.mealHistory` read-only until Task 12 exports and reconciles it. Do not sum those old entries into version 2 without a reviewed identity and deduplication rule.

Before production migration, back up meals, students, and feedback. Inventory existing rating counts and embedded history, resolve duplicate student/meal identities, create the feedback indexes, and reconcile all summary fields. Task 12 owns the data migration. The local 20-voter test is a functional concurrency check; it is not a production capacity result. Measure latency, transaction retries, storage, and index write cost against representative staging data before setting a load target.
