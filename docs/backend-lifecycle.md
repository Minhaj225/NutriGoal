# Backend startup and readiness

`backend/app.js` exports the Express app without connecting or listening. `npm start` runs `backend/server.js`, which waits for the rate limiter and MongoDB before opening the local listener. It closes the listener before disconnecting MongoDB on SIGINT/SIGTERM. The Vercel handler imports the same app and waits for one shared in-flight MongoDB connection on a cold request. A failed connection returns 503; a later request may retry.

`GET /api/health` is cheap liveness. `GET /api/ready` reports database readiness and the configured recommender mode; it returns 503 when MongoDB is disconnected. Behavioral model configuration is reported separately and does not make the baseline unavailable. The Home page uses readiness for its status display. The app no longer exposes its internal ML URL through `/api`.

The connection starts with a maximum pool of 5, a minimum of 0, a 3-second server-selection timeout, and a 5-second socket timeout per process. Read-only list/detail queries have a 5-second query deadline; meal and feedback lists have bounded pages and stable `_id` tie ordering. These values need measurement against the actual Atlas tier and deployment concurrency. Statistics query the current database state without an in-process cache and divide verified rating sums by the count of verified ratings; no votes returns `null` and a count of zero.

Production auto-indexing is disabled. Apply and review schema indexes as an explicit maintenance operation after the catalogue remap and uniqueness audit, using an isolated copy first. Do not infer index effectiveness from the small local fixtures: capture `explain('executionStats')` on representative larger data, including active meal sorts/filters and student lookup, before deciding on new compound indexes. Record the write/storage cost. A staged cold/warm request, dependency outage, pool use, and query timing check remains necessary before release; local mocked and isolated tests do not verify Vercel or Atlas behavior.
